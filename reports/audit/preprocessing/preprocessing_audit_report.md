# Phase 1 preprocessing audit: ActRef master dataset

Generated by `src/data/audit_preprocessing.py` on 2026-10-31. **Analysis only:** no transformation was applied to the data, no model was trained, no split was saved, and the master dataset was only read through `src/data/load_master.py` (checksum verified before and after). Feature sets come from `src/features/feature_sets.py`. Every number below is computed by the script; the CSV files in this folder hold the full tables.

## 1. Executive summary

- **The data is clean.** 31,209 rows, 243 renamed / 30,966 not renamed (0.78%), 46 features, 323 project groups. No missing, non-numeric or infinite values; no duplicate keys or rows; every binary, ratio and count feature holds only valid values. **No imputation or cleaning is needed.**
- **Code metrics are heavily right-skewed** (19 of 27 non-binary features have |skewness| > 2) with genuine extreme values (e.g. a 91-parameter function). Outliers are real code, not errors: **keep them.** `log1p` (counts) and `asinh` (signed relative features) remove most of the skew and matter only for Logistic Regression; tree models need no transformation or scaling.
- **Class differences are small.** Apart from the two file-size features (Cliff's δ ≈ -0.43 / -0.39), every feature has |δ| ≤ 0.17. 11 of 42 features have a project-level bootstrap interval that excludes zero.
- **Redundancy is real but bounded.** Two exact identities (`has_docstring` ≡ `doc_len > 0`, `in_class` ≡ `class_n_methods > 0`) and a name-length cluster; VIF up to 17.9 (main set). Transforms reduce some VIFs but not all (max 25.3 after transforms), so **Logistic Regression needs L2 regularization**.
- **Grouped validation is feasible.** 79 of 323 projects contain positives (median 2, max 19); the top 5 hold 28% of all positives. Across 50 simulated seeds a 20% project hold-out keeps 47–50 positives from 10–17 positive projects, and each inner fold keeps 37–41 positives. Because the test estimate rests on few positive projects, report project-level uncertainty.
- **Class imbalance:** use training-fold class weights (balanced weight for positives ≈ 64); no SMOTE or resampling.

## 7. Grouped validation feasibility

Simulated with `StratifiedGroupKFold(n_splits=5, shuffle=True)` over 50 seeds, grouping on `meta_project_group`; for the hold-out design one outer fold (≈ 20% of rows) is the test set and a second 5-fold split runs on the rest. Every simulation asserts that no project appears in two partitions. **No split was saved.** Per-seed results: `grouped_cv_feasibility.csv`.

| Quantity | Range across 50 seeds |
|---|---|
| 5-fold on all data: positives per fold | 47–50 |
| 5-fold on all data: rows per fold | 6239–6247 |
| 5-fold on all data: positive projects in the smallest fold | 10–15 |
| 20% hold-out: rows | 6239–6245 |
| 20% hold-out: projects | 58–66 |
| 20% hold-out: positives | 47–50 |
| 20% hold-out: positive projects | 10–17 |
| Development set: positives | 193–196 |
| Inner 5-fold on development set: positives per fold | 37–41 |

Assessment:

- **5-fold StratifiedGroupKFold is feasible**: positives are spread almost evenly (47–50 per fold) and every fold has at least 10 positive projects.
- **A 20% project hold-out is feasible** and leaves ≈ 194 positives for development with 37–41 per inner fold, but the test estimate rests on only 10–17 positive projects; a single project (e.g. `streamlit`, 19 positives) can move the test score noticeably. Recommendation: fix the hold-out once (one seed), report a project-level bootstrap interval on it, and use repeated grouped CV on the development set as the main model-selection evidence.
- Row-level random splitting is not used; grouping by `meta_project_group` also keeps the repeated-method clusters together (0 clusters span two groups).

## 9. Leakage prevention in the future pipeline

1. **Split first.** Assign project groups to hold-out / development and to folds before any fitting; a project never appears in two partitions; splits store keys and fold numbers only (`data/processed/splits/`).
2. **Fit on training folds only.** Scalers, any fitted transform (e.g. Yeo-Johnson), optional winsorizing thresholds, class weights and the decision threshold are fitted on the training part of each fold and applied unchanged to its validation part; the hold-out is used once at the end.
3. **One pipeline object.** Put transforms, scaler and model in a single scikit-learn `Pipeline`, so cross-validation refits everything per fold automatically.
4. **Clean X.** Build X only with `select_xy_groups(df, 'main' | 'comparison')`; identifiers, the target, `meta_*` columns (including `meta_project_group`) and the excluded/dropped features are rejected by `validate_feature_set()`.
5. **Immutable master.** Load through `load_master()`, which verifies the SHA-256; never write to the master.
6. **No look-ahead in this audit's numbers.** Statistics in this report use the full data and are descriptive; they must not be used to fit anything (for example, the skewness here only chooses *which* stateless transform to try; it supplies no fitted parameter).

## 11. Known limitations and unresolved questions

- 76 of the 243 positives are AI-reviewed and not confirmed by a person; every statistic involving positives inherits that uncertainty.
- With 243 positives, effect sizes and rare-binary rates are imprecise; project clustering widens the intervals further.
- 27 rows (9 clusters) have identical features but different labels: an upper bound on achievable separation with these features.
- Scope: methods in files edited by the future commit; about 9.5% of methods with unknown outcomes are excluded.
- Open decisions: transform choice for LR (log1p/asinh vs Yeo-Johnson), whether to run the winsorizing sensitivity check, and the hold-out seed and fold settings.
